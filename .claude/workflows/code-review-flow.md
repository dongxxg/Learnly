# 代码评审流程 (Code Review Flow)

## 流程概述
代码评审流程定义了代码评审的详细步骤，确保评审的质量和效率。

## 详细流程说明

### 1. 接收评审任务
- 从主会话接收评审任务
- 获取待评审的代码/设计
- 了解评审范围和标准

### 2. 理解评审范围
- 读取相关文档
- 理解功能需求
- 确认评审重点

### 2.5. 第一阶段：规范合规评审 `<HARD-GATE>`

**此阶段必须在代码质量评审之前完成。不合规 = 阻断，不进入代码质量评审。**

检查项:

1. **验收标准覆盖**: 逐条对照 Spec 验收标准，确认代码是否满足每一条
2. **未授权变更**: 检查是否存在 Spec 中未定义的新增文件/模块/重构
3. **遗漏检查**: 是否存在 Spec 明确要求的验收标准未实现
4. **越界检查**: 是否实现了 Spec 范围之外的功能（YAGNI 违规）
5. **围栏违规**: 是否违反 Karpathy 行为围栏（假设需求、为未来预留）
6. **TDD 合规检查**: 检查是否存在越狱行为——是否有测试代码、测试是否覆盖所有新增行为、commit 历史是否为"先写代码后补测试"模式

合规判定:
- 全部通过 → 进入第二阶段（代码质量评审）
- 存在 SPEC_GAP → 阻断，返回 Developer 修复
  - 明确标注 gap 位置（文件名:行号）和具体遗漏项
  - **修复后必须重新进入第一阶段**，不得直接跳到第二阶段

### 3. 第二阶段：代码质量评审（评分卡）`<HARD-GATE>`

**仅在第一阶段合规通过后才能进入。**

#### 3.1 代码规范检查（20分）
| 检查项 | 分值 | 检查方法 |
|--------|------|----------|
| 命名规范 | 5 | 检查变量/函数/类名 |
| 代码风格 | 5 | 检查格式一致性 |
| 注释文档 | 5 | 检查注释质量和数量 |
| 代码组织 | 5 | 检查文件和目录结构 |

#### 3.2 性能检查（20分）
| 检查项 | 分值 | 检查方法 |
|--------|------|----------|
| 算法复杂度 | 8 | 分析循环和递归 |
| 资源使用 | 6 | 检查内存/IO/网络 |
| 缓存策略 | 6 | 评估缓存使用 |

#### 3.3 安全检查（25分）
| 检查项 | 分值 | 检查方法 |
|--------|------|----------|
| 输入验证 | 8 | 检查输入清理和验证 |
| 权限控制 | 8 | 检查权限检查 |
| 敏感数据处理 | 9 | 检查加密和存储 |

#### 3.4 可维护性检查（25分）
| 检查项 | 分值 | 检查方法 |
|--------|------|----------|
| 代码可读性 | 9 | 评估代码清晰度 |
| 模块耦合度 | 8 | 分析依赖关系 |
| 依赖管理 | 8 | 检查依赖清晰度和合理性 |

#### 3.5 测试质量检查（10分）
| 检查项 | 分值 | 检查方法 |
|--------|------|----------|
| 测试覆盖率 | 5 | 检查覆盖率百分比 |
| 测试有效性 | 5 | 评估测试用例质量 |

### 4. 计算质量得分
- 汇总各维度得分
- 计算总分（满分100）
- 记录各得分项

### 5. 判断是否需要触发对抗审计

#### 质量门禁阈值策略（AD-014 调整后）：
```
得分 ≥ 90: 【直接通过】 - 继续流程
80 ≤ 得分 < 90: 【Review处理】 - Reviewer处理非P0问题后通过
75 ≤ 得分 < 80: 【触发对抗审计】 - 进行Defender/Attacker对抗
得分 < 75: 【直接返工】 - 不触发对抗审计，直接返回返工
```

**调整说明**：
- 原 70-80 区间调整为 75-80
- 得分 <75 直接返工（论据质量不对称，Debate 价值低）
- PM 仍可主动触发 Debate（AD-013）

#### 回退触发器（AD-019 返工目标明确化版）：
| 触发条件 | 返工类型 | 返工目标角色 | 判断依据 |
|----------|----------|--------------|----------|
| 得分 < 75（架构/设计问题为主） | 阻断返工 | Architect（重新设计）| - 系统拓扑不合理<br>- 接口定义缺失<br>- 技术选型错误 |
| 得分 < 75（代码/测试问题为主） | 阻断返工 | Developer（修复代码）| - 代码覆盖率<80%<br>- 测试失败<br>- 代码质量问题 |
| 得分 < 75（技术规范问题为主） | 阻断返工 | Architect（修正规范）| - 类型定义缺失<br>- 命名不一致<br>- 模板错误 |
| 存在P0安全问题 | 安全返工 | Architect/Developer | - 认证/授权缺失<br>- 数据加密不足<br>- 权限控制漏洞 |
| 测试覆盖率 < 80% | 测试返工 | Developer | - 测试用例不足<br>- 边界情况未覆盖 |
| 架构一致性 < 80 | 架构返工 | Architect | - 与设计决策不符<br>- 模块依赖混乱 |

**AD-019 返工目标明确化**：
- 主会话必须在返工时记录问题维度（架构/代码/规范/安全）
- 在progress.md中明确记录返工原因和目标角色
- 返工任务必须包含可验收的修复标准

#### 需要触发对抗审计的情况：
- 质量得分在 75-80 之间（AD-014 调整后）
- 存在争议的设计决策（无明确对错）
- 安全/性能关键功能的评审
- 明确标记为"需论证"
- PM 主动触发（AD-013，不受得分限制）

#### 不需要触发对抗审计的情况：
- 质量得分 >= 90
- 质量得分 < 75（直接返工）
- 简单功能的评审
- 明确的质量问题

### 6. 生成评审报告
按照评分卡模板生成详细报告，包含：
- 质量得分
- 各维度得分
- 问题清单（按严重程度分类）
- 评审结果（通过/需修改/阻断/需对抗审计）
- 改进建议

### 7. 提交主会话
- 提交评审报告
- 说明是否触发对抗审计
- 提供改进建议

## 评审结果处理

### 通过
- 总分 >= 80
- 无严重问题
- 高问题 <= 2个
- 动作：继续流程

### 需修改
- 总分 75-79
- 或存在一些高问题
- 动作：触发对抗审计

### 阻断
- 总分 < 75
- 或存在严重问题
- 动作：按问题维度确定返工目标（架构→Architect，代码→Developer，规范→Architect）

### 需对抗审计
- 质量得分 75-80（AD-014 调整后）
- 或存在争议
- 动作：触发对抗审计（Defender→Attacker→主会话裁决）

## 评审检查清单

### 评审前
- [ ] 已阅读相关文档
- [ ] 已理解功能需求
- [ ] 已确认评审范围

### 评审中
- [ ] 按评分卡逐项检查
- [ ] 记录所有发现的问题
- [ ] 评估问题严重程度
- [ ] 提供具体改进建议

### 评审后
- [ ] 计算质量得分
- [ ] 生成评审报告
- [ ] 判断是否触发对抗审计
- [ ] 提交主会话

## 问题严重程度定义（AD-018 一票否决版）

| 级别 | 描述 | 示例 | 是否阻断 | 触发动作 |
|------|------|------|----------|----------|
| **P0** | 安全漏洞、规范自相矛盾、核心定义缺失 | SQL注入、XSS、规则与示例矛盾、必填字段未定义 | 是 | **一票否决**，总分归零，直接阻断返工 |
| **P1** | 性能问题、重要逻辑缺陷 | O(n²)复杂度、内存泄漏、校验规则缺失 | 否 | 高优修复，影响最终得分 |
| **P2** | 代码质量、文档质量问题 | 硬编码、命名不规范、注释不足 | 否 | 可延后修复 |

**AD-018 一票否决机制**：
- 发现任何P0问题时，质量得分直接归零
- 触发阻断返工，不触发对抗审计
- 返工目标：Developer（代码问题）、Architect（架构问题）、Architect（规范问题）

## 与其他流程的集成

### 与Development Flow集成
- 在Developer完成后触发
- 评审结果决定下一步行动
- 可触发对抗审计进行深入讨论

### 与对抗审计集成
- 评审报告作为对抗审计输入
- 评审发现的问题作为对抗审计焦点
- 对抗审计结论补充评审结果

## 评审效率优化

### 快速评审
- 小型变更（<100行）
- 简单功能
- 明确的修改

### 完整评审
- 大型变更（>500行）
- 复杂功能
- 架构性变更

### 重点评审
- 安全相关
- 性能关键
- 高风险功能

## 评审质量保证

### 评审者要求
- 熟悉项目架构
- 了解业务需求
- 掌握评分卡标准

### 评审一致性
- 使用统一的评分卡
- 统一的问题严重程度定义
- 统一的评审报告格式

### 评审跟踪
- 记录所有评审
- 跟踪问题修复
- 分析评审趋势

## 常见评审陷阱

### 避免过度挑剔
- 专注于关键问题
- 提供建设性反馈
- 平衡质量与效率

### 避免主观判断
- 基于事实和证据
- 使用明确的检查项
- 避免个人偏好

### 避免评审疲劳
- 合理分配评审任务
- 使用工具辅助
- 适当聚焦重点
