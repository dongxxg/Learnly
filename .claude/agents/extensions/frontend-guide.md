# Frontend 开发指南

> Developer 专用的前端开发扩展。当任务涉及前端开发时加载。

# IRON LAW: 未经浏览器验证的组件 = 未完成

组件必须在浏览器中实际渲染并截图确认后，才能声称完成。

## 前端特有职责

### 1. 组件开发
- 按设计稿实现 UI 组件，遵循项目已有的组件模式和样式规范
- 组件职责单一，可组合，props 类型完备
- 用 TypeScript 确保类型安全，禁止 `any`（除非确实无法推断且已注释原因）

### 2. 状态管理
- 按项目现有方案（Redux / Zustand / Context / Jotai 等），不另起炉灶
- 区分 UI 状态（组件内部）和业务状态（全局 store）
- 异步数据请求覆盖 loading / error / empty 三种状态

### 3. 错误处理
- 每个页面级组件必须有 error boundary 包裹
- 数据请求必须有错误兜底 UI，不能白屏
- 关键操作（表单提交、删除）失败后有用户可感知的错误提示

### 4. 响应式与样式
- mobile-first 思维，按项目约定的断点适配
- 暗色模式/主题切换兼容
- 优先使用项目已有的 design token 和 CSS 变量

### 5. 性能
- 路由级 lazy loading + code splitting
- 图片懒加载、字体子集化、静态资源压缩
- 关注 Core Web Vitals（LCP / FID / CLS），避免布局偏移

### 6. 可访问性
- 语义化 HTML 标签
- ARIA 属性正确使用
- 键盘导航可用，焦点管理合理

### 7. 浏览器验证
- 启动 dev server，在浏览器中实际渲染
- 截图确认关键页面和交互状态
- 覆盖目标浏览器（Chrome / Safari / Firefox 至少两个）

## 前端开发流程

```
接收任务 → 启动 dev server → TDD 循环 → 浏览器验证 → 截图 → 报告
```

### TDD 循环（前端特化）

**RED 阶段：**
- 为组件行为编写测试
- 测试渲染输出、交互响应、状态变化

**GREEN 阶段：**
- 实现组件使测试通过
- 最小实现，不追求完美

**REFACTOR 阶段：**
- 改善组件结构
- 提取可复用逻辑
- 优化样式组织

### 浏览器验证

1. **启动 dev server**
   ```bash
   npm run dev
   # 或项目特定的启动命令
   ```

2. **验证关键状态**
   - 正常渲染
   - Loading 状态
   - Error 状态
   - Empty 状态

3. **截图确认**
   - 每个关键状态一张截图
   - 跨浏览器验证（至少两个）

## 反模式自检

| 借口 | 现实 |
|------|------|
| "这样式太简单，不用浏览器看" | 没在浏览器看到 = 没完成。CSS 在不同环境的渲染结果不一样。 |
| "Chrome 通过了 Safari 应该没问题" | 浏览器差异是前端的核心复杂度。至少覆盖两种引擎。 |
| "类型用 any 方便" | any 传染。类型安全是前端的底线，写 any 必须注释原因。 |
| "loading 状态后面补" | 用户等 loading 的时间比"后面补"来得更早。三态全覆盖。 |
| "截图太麻烦" | 一张截图顶一百行描述。截图 = 证据。 |

## 退出状态（前端特化）

| 状态 | 说明 |
|------|------|
| DONE | 组件开发完成，浏览器验证通过，测试全部通过，截图已产出 |
| DONE_WITH_CONCERNS | 组件完成但存在疑虑（如性能未达标、可访问性部分未覆盖） |
| NEEDS_CONTEXT | 缺少设计稿或交互说明 |
| BLOCKED | 依赖的后端 API 不可用、设计稿有矛盾无法继续 |

## 报告格式（前端特化）

```markdown
## 前端实现报告
- 任务信息：[任务描述]
- 实现文件：[组件文件列表]
- 测试情况：[测试结果]
- 浏览器验证：[Chrome ✓, Safari ✓, Firefox ✗]
- 截图：[关键状态截图路径]
- 已知问题：[如有]
```

## 与其他角色协作

### → Architect
- 需要明确组件接口和状态结构
- 确认设计稿的完整性

### → Developer
- 后端 API 接口定义
- 数据类型约定

### → Reviewer
- 组件可复用性
- 性能和可访问性评估
