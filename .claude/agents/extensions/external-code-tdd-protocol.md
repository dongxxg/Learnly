# External Code TDD Protocol

> 处理 PM / 同事提供的现有代码时的 TDD 流程

## 场景定义

当任务中包含 PM 或同事提供的代码时，不能直接假设这些代码正确。

## 处理流程

### 第一步：评估现有代码

1. **检查是否有测试**
   - 如果有测试：验证测试覆盖度
   - 如果无测试：需要添加

2. **识别需要修改的部分**
   - 明确哪些代码需要修改
   - 明确哪些代码可以保持不变

### 第二步：为现有代码编写测试

1. **编写保护性测试**
   - 为现有代码编写测试
   - 确保现有行为被捕获
   - 这将成为修改的安全网

2. **验证测试通过**
   - 在修改之前，测试必须通过
   - 这证明了测试正确捕获了现有行为

### 第三步：编写新功能/修复的测试

1. **编写新测试**
   - 为需要添加的功能编写测试
   - 或为需要修复的 bug 编写复现测试

2. **验证新测试失败**
   - 确认新测试失败（因为功能未实现）

### 第四步：实现和验证

1. **实现功能**
   - 按照标准 TDD 流程进行
   - 先通过保护性测试，再通过新测试

2. **验证所有测试**
   - 所有旧测试仍然通过
   - 所有新测试通过

## 特殊情况

### 情况 1：现有代码有 bug

如果发现现有代码有 bug：

1. 先记录发现的问题
2. 向 PM 确认是否修复
3. 如果修复，先为 bug 编写测试
4. 然后修复 bug

### 情况 2：现有代码质量差

如果现有代码质量差（难以测试）：

1. 记录质量问题
2. 向 PM 报告
3. 请求明确：是否重构后再修改

### 情况 3：现有代码不符合规范

如果现有代码不符合规范：

1. 记录不符合规范的地方
2. 向 PM 报告
3. 请求明确：是否修复规范问题

## 禁止行为

❌ 假设现有代码正确而不测试
❌ 直接修改现有代码而不添加测试
❌ 跳过保护性测试
❌ 忽略现有代码中的问题

## 验证标准

完成处理后：

- [ ] 现有代码有测试保护
- [ ] 所有测试通过
- [ ] 新功能/修复有测试
- [ ] 没有破坏现有功能
- [ ] 已记录所有发现的问题
