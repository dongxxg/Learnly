## 编码规范

### 通用原则
- **命名清晰**: 变量、函数、类名要能清晰表达意图
- **函数短小**: 单个函数不超过50行
- **避免重复**: 遵循DRY原则
- **早期返回**: 减少嵌套层级

### 代码组织
```
src/
├── components/     # 可复用组件
├── services/       # 业务逻辑
├── utils/          # 工具函数
├── types/          # 类型定义
├── constants/      # 常量定义
└── tests/          # 测试文件
```

### 注释规范
- **复杂逻辑**: 解释"为什么"而非"是什么"
- **公共API**: 必须有清晰的文档注释
- **TODO标记**: 标记待办事项和已知问题

## 测试规范

### 测试金字塔
- **单元测试**: 覆盖核心逻辑（占比70%）
- **集成测试**: 覆盖组件交互（占比20%）
- **端到端测试**: 覆盖关键流程（占比10%）

### 测试命名
```javascript
// 好的命名
describe('UserService', () => {
  describe('createUser', () => {
    it('should create user with valid data', () => {});
    it('should throw error when email exists', () => {});
  });
});
```

### 测试覆盖率要求
- 核心业务逻辑: 100%
- 公共API: 90%
- 工具函数: 80%
- 总体: > 80%

## 常见问题处理

### 性能问题
- 使用profiler定位瓶颈
- 考虑缓存策略
- 优化算法复杂度
- 避免不必要的计算

### 并发问题
- 识别共享状态
- 使用适当的同步机制
- 避免死锁
- 考虑并发模式

### 安全问题
- 输入验证和清理
- 防止SQL注入/XSS
- 敏感数据加密
- 遵循最小权限原则

## 分支收尾阶段（finishing-a-development-branch）

> 本章节基于 Git 版本控制设计，非 Git 项目不适用。

**触发条件**（全部满足才执行收尾）：
- 退出状态为 DONE 或 DONE_WITH_CONCERNS（退出状态定义见 harness-rules.md）
- 所有分配给你的任务已完成（通过 TaskList 确认无 pending 任务）
- 你在特性分支上工作（当前分支 ≠ main/master）

**不满足触发条件时**：在报告末尾写"收尾条件未满足，跳过分支收尾建议"即可。

**你不执行任何修改仓库状态的 git 操作**（commit/push/merge/checkout/branch-D/worktree-remove）。只读查询命令（status/log/branch/diff/rev-list 等）允许执行，仅用于信息采集。这是单向信息输出——你发完报告即结束，不等待回复。

> **时序说明**：此建议基于当前 Developer 完成状态输出。如后续 Tester/Reviewer 评审发现问题需返工，收尾建议需重新评估，之前的建议自动失效。

### 字段填写说明

以下信息你需要在输出模板前先获取：

| 字段 | 获取方式 |
|------|---------|
| 当前分支 | `git branch --show-current` |
| 基线分支 | `git symbolic-ref refs/remotes/origin/HEAD 2>/dev/null \|\| git config init.defaultBranch \|\| echo "无法自动检测"` |
| 领先提交数 | `git rev-list --count origin/{基线分支}..HEAD 2>/dev/null \|\| echo "未知"` |
| 变更摘要 | `git log --oneline origin/{基线分支}..HEAD 2>/dev/null \|\| echo "无法获取"` |
| 工作模式/路径 | `git worktree list` 判断是否为 worktree |
| 工作树状态 | `git status --short` 统计已修改和未追踪文件数 |

### 收尾建议格式

在完成报告末尾追加以下内容。根据你的退出状态选择对应的推荐选项段落：

**[退出状态为 DONE 时，输出以下选项 1-4]**

```markdown
## 分支收尾建议

> 此建议基于 Developer 当前完成状态，后续 Tester/Reviewer 评审结果可能导致建议变更。

**分支状态**:
- 当前分支: {分支名}
- 基线分支: {检测到的基线分支名}
- 领先提交数: {N} 个
- 变更摘要: {每个提交的 oneline 摘要，每条提交一行}
- 工作模式: {主仓库 / worktree（附绝对路径）}
- 工作树状态: {clean / N 个已修改文件, M 个未追踪新文件}

**推荐选项**（由主会话/PM 执行）:
1. 合并到基线分支（需先切换到基线分支再合并，完成后删除开发分支）
2. 推送并创建 Merge Request（需 PM 确认推送）
3. 保持现状（稍后手动处理）
4. 丢弃本次工作（仅在代码质量不达标或需求废弃时适用，需 PM 二次确认）

**说明**: 以上操作均由主会话/PM 执行，Developer 不执行任何 git 写操作。
```

**[退出状态为 DONE_WITH_CONCERNS 时，用以下选项替换上方的选项 1-4]**

```
**推荐选项**（由主会话/PM 执行）:
1. [不推荐] 合并到基线分支（存在未解决疑虑，建议主会话先处理疑虑后再决定）
2. 推送并创建 Merge Request（需 PM 确认推送）
3. [推荐] 保持现状（待疑虑处理后再决定）
4. 丢弃本次工作（仅在代码质量不达标或需求废弃时适用，需 PM 二次确认）
```

### 主会话执行参考

| 选项 | 需测试通过 | 合并 | 推送 | 保留分支 | 清理 worktree |
|------|-----------|------|------|---------|--------------|
| 1. 合并 | ✓ | ✓（需先切换到基线分支） | — | — | ✓ |
| 2. MR | ✓ | — | ✓（需 PM 确认） | ✓ | — |
| 3. 保持现状 | — | — | — | ✓ | — |
| 4. 丢弃 | — | — | — | — | ✓（需 PM 二次确认） |

### 红线

- 退出状态非 DONE/DONE_WITH_CONCERNS → 不输出收尾建议
- 当前分支为 main/master → 不输出收尾建议
- 还有未完成任务 → 不输出收尾建议
- 你不执行任何修改仓库状态的 git 操作（commit/push/merge/checkout/branch-D/worktree-remove）。只读查询命令除外。
