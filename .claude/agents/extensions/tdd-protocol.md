# TDD Protocol (Test-Driven Development)

> Developer 专用的 TDD 详细流程

## IRON LAW

**NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST**

## TDD 循环：RED → GREEN → REFACTOR

### RED 阶段

1. **理解需求**
   - 阅读 SPEC 中的需求描述
   - 明确输入、输出、边界条件
   - 如有疑问，向 PM 澄清

2. **编写失败测试**
   - 先写测试，不写实现
   - 测试必须明确失败
   - 验证测试确实失败

3. **验证失败原因**
   - 确认失败是因为功能未实现
   - 而不是测试本身有问题

### GREEN 阶段

1. **最小实现**
   - 编写最简单的代码使测试通过
   - 不考虑优雅性，只考虑通过
   - 不要优化

2. **验证通过**
   - 运行测试，确认通过
   - 检查是否有副作用

### REFACTOR 阶段

1. **代码优化**
   - 在保持测试通过的前提下优化代码
   - 改善结构、可读性
   - 消除重复

2. **持续验证**
   - 每次重构后运行测试
   - 确保测试仍然通过

## 常见场景

### 场景 1：新功能

```
RED: 编写新功能的测试
GREEN: 实现新功能
REFACTOR: 优化代码结构
```

### 场景 2：Bug 修复

```
RED: 编写复现 bug 的测试
GREEN: 修复 bug
REFACTOR: 检查相关代码
```

### 场景 3：重构

```
RED: 确保现有测试覆盖
GREEN: 不涉及（已有测试）
REFACTOR: 执行重构
```

## 禁止行为

❌ 先写代码，后补测试
❌ 跳过测试直接实现
❌ 测试和实现一起写
❌ 为了通过测试而降低测试标准

## 外部代码场景

当 PM 提供现有代码时：

1. 先为现有代码编写测试
2. 确保测试覆盖需要修改的部分
3. 然后按照 TDD 流程进行修改

详细流程见：`external-code-tdd-protocol.md`

## 验证标准

完成 TDD 循环后：

- [ ] 所有测试通过
- [ ] 测试覆盖了需求
- [ ] 代码清晰可读
- [ ] 没有重复代码
- [ ] 没有待办事项（TODO）
