# 代码精简 — 并行评审与清理

用三个专注的评审者并行审查你的代码变更，聚合发现并应用值得修复的问题。

**核心原则：** 三个窄聚焦的评审者优于一个宽泛的评审者。每个评审者深挖单一问题领域——复用、质量、效率——不会分散注意力。并行运行，只需一次评审的耗时，获得三份产出。

## 何时使用

以下任一场景触发本技能：

- "精简" / "精简我的代码" / "精简这些改动"
- "review 代码" / "审查代码" / "清理代码"
- "/simplify"

可选修饰符（按用户意图调整）：

- **聚焦：** "只关注效率" → 仅运行效率评审者。支持的聚焦领域：`reuse`（复用）、`quality`（质量）、`efficiency`（效率）。
- **dry run：** "只报告别改" / "只看不动" → 跑三个评审者，展示发现，不应用任何修改。应用前先询问。
- **范围：** "精简最后一次提交" / "精简暂存区" / "精简 src/foo.ts" → 按指定范围缩小 diff（见阶段 1）。

**不要**在每次编辑后自动运行。每次运行消耗三个 sub-agent 的 token——仅在用户明确要求时触发。

## 流程

### 阶段 1 — 识别变更

抓取要审查的 diff。按用户要求的来源选取，默认按以下顺序：

```bash
# 1. 默认：未提交的工作区改动（已跟踪文件）
git diff

# 2. 如果为空，包含暂存区改动
git diff HEAD

# 3. 用户可能要求的限定范围：
git diff --staged              # "暂存区改动"
git diff HEAD~1                # "最后一次提交"
git diff main...HEAD           # "这个分支" / "我的 PR"
git diff -- src/foo.py         # 指定文件
```

如果 `git diff` 和 `git diff HEAD` 都为空，且没有 git 仓库或无改动，回退到用户明确指定的文件或本次会话最近创建/编辑的文件。如果确实找不到任何变更代码，直接告知用户并停止——没有需要精简的内容。

捕获完整 diff 文本。注意大小：如果 diff 很大（比如超过 2000 行改动），提示用户三个 sub-agent 各携带完整 diff 会消耗大量 token，建议在继续前缩小范围（按目录、按提交）。

### 阶段 2 — 并行启动三个评审者

> **Dispatch 约束**
> - 本 skill 是**手动触发的 ad-hoc 工具**，不走 rd-auto pipeline，因此**不通过** `dispatch-agent.js` wrapper（wrapper 是 pipeline 强制入口，由 `advance` 命令校验 `wrapper_invoked` 字段，参见 `${HARNESS_ROOT:-.claude}/skills/rd-auto/SKILL.md` §"主会话 backend 分流"）。
> - 当前实现用 `delegate_task` 的 batch 模式直接并行调度 3 个 sub-agent，与 `code-review` 阶段（pipeline 内 reviewer 角色）是**两套独立机制**——不写 `pipeline-state.json`、不参与 P0 veto。
> - **Codex 后端差异**：在 `HARNESS_BACKEND=codex` 下，`delegate_task` 的 batch 行为可能不一致（参见 `${HARNESS_ROOT:-.claude}/backends/codex-backend.js`）。若 3 路并行失败，降级为串行调用，每个 sub-agent 跑完再启动下一个。
> - **change-name 落盘（可选）**：若希望把发现归档到 shared-state，可在阶段 3 聚合后调用：
>   ```bash
>   node ${HARNESS_ROOT:-.claude}/skills/rd-auto/scripts/orchestrator.js write-shared-state <change-name> --key concerns
>   ```
>   change-name 由 PM 指定（如 `simplify-review-<date>`），未指定则不落盘（ad-hoc 调用默认不落盘）。

使用 `delegate_task` **batch 模式**——一次性传入三个任务数组，并行运行。

给**每个**评审者**完整的 diff**（不分片——跨文件问题只在全局视角下暴露），加上仓库绝对路径以便搜索更广的代码库。每个评审者有 `terminal`、`file` 和 `search` 工具集。

告知每个评审者：
- 搜索已有代码库寻找证据（不只看 diff 猜测）。
- **遵守 Chesterton's Fence（切斯特顿栅栏原则）：** 在标记任何东西之前，对改行跑 `git blame` 理解它为什么存在。如果无法确定原始目的，标记 `confidence: low`——别猜。
- 用结构化输出报告发现，含置信度和风险：
  ```
  file:line → 问题 → 建议修复 | 置信度: high/medium/low | 风险: SAFE/CAREFUL/RISKY
  ```
  - **SAFE** = 可证明不影响行为（未使用的 import、被注释的代码、纯透传 wrapper）。自动应用。
  - **CAREFUL** = 改进但不改变语义（重命名局部变量、展平嵌套三元、提取辅助函数）。带测试验证后应用。
  - **RISKY** = 可能改变行为或破坏公共接口（N+1 重构、公共 API 重命名、内存生命周期变更）。标记供人工审查——**不**自动应用。
- 跳过琐碎的风格变更。只标记对代码有实质改进的问题。

传入以下三个目标（如果用户聚焦排除了某个，则跳过对应的）：

**评审者 1 — 代码复用**
> 审查此 diff 中与代码库已有实现重复的代码。搜索工具模块、共享辅助函数和相邻文件（用 search_files / grep）中已有的函数、常量或模式，新代码可以调用它们而不是重复实现。标记：新增的重复函数；手写的能被已有工具函数替代的逻辑（手动字符串/路径操作、自定义环境检查、临时类型守卫、重新实现的解析逻辑）。对每一处，指出该用什么已有实现以及它在哪里。

**评审者 2 — 代码质量**
> 审查此 diff 中的质量问题。关注：冗余状态（可以从已有状态推导的值；不需要存在的缓存）；参数膨胀（不断加参数而函数本应重构）；改改就粘贴（近乎相同的代码块应共享抽象）；泄露抽象（暴露内部实现、破坏已有封装边界）；字符串滥用（原始字符串的地方已有常量/枚举/注册表——先查已有注册表再标记）；AI 生成代码的常见冗余（对显而易见的代码加注释比如 `// 递增计数器` 配 `count++`；已校验输入的冗余 null 检查；绕过类型系统的 `as any` 转换；与文件其他部分不一致的模式）。对每处问题给出具体的重构方案。

**评审者 3 — 执行效率**
> 审查此 diff 中的效率问题。关注：不必要的工作（重复计算、重复读文件、重复 API 调用、N+1 访问模式）；错失的并发机会（独立操作串行执行）；热路径膨胀（启动或每次请求路径上的重/阻塞操作）；TOCTOU 反模式（存在性预检查后再操作，应直接操作然后处理错误）；内存问题（无限增长、缺少清理、监听器/句柄泄露）；过度读（读取整个文件而只需一部分）；沉默失败（空 catch 块、忽略的错误返回值、`except: pass`、`.catch(() => {})` 没有处理、错误传播缺口——这些问题隐藏 bug，至少应该在吞掉之前记录日志）。对每处给出具体的修复方案以及为什么更快或更安全。

### 阶段 3 — 聚合与应用

> **Apply 权限边界**
> - 自动 apply 仅限 **SAFE 层**（未使用 import、注释代码、透传 wrapper）；**CAREFUL/RISKY 层必须 PM 显式确认**后才能应用。
> - 一次 simplify 跑完产出的修复**必须按 atomic commit 粒度拆分**（参见 `${HARNESS_ROOT:-.claude}/rules/ai-git-commit-spec.md`）：每条修复一个独立 commit，message 用 `[<task-id>] REFACTOR <module>[AI-<user>.Developer]`。
> - **禁止**把 simplify 修复与业务变更揉进同一个 commit——会让 review 失焦。
> - dry-run 模式下不 apply，只产出报告；PM 决定后续是否手动应用。

等待三个评审者全部返回（batch 模式一次性返回）。

1. **合并**发现到一个列表，去重。
2. **丢弃误报**——你有最完整的上下文；不需要和评审者争论，对弱或错误的建议默默抛弃。
3. **解决冲突。** 评审者可能意见不同（评审者 1："用已有工具函数 X"；评审者 3："X 慢，内联它"）。默认优先级：**正确性 > 用户指定的聚焦 > 可读性/复用 > 微性能。** 除非某个路径确实是热路径，否则别为了性能牺牲清晰度。当两个建议互斥且都有理由时，选改动最小的方案，并备注替代方案。
4. **按风险层级应用：**
   - **SAFE 优先**（自动应用）：未使用的 import、被注释的代码、透传 wrapper、冗余类型断言。之后跑测试。
   - **CAREFUL 其次**（一个一个文件应用，带验证）：重命名局部变量、展平三元、提取辅助函数、合并重复。每改一个文件就跑测试，回滚任何失败的。
   - **RISKY 最后**（标记供审查——**不**自动应用）：N+1 重构、公共 API 变更、并发修复、错误处理变更。每项附带风险描述和测试覆盖状态。
   如果用户选了 dry run，展示三个层级但不应用任何修改。
5. **验证**没有破坏东西：跑改动文件的目标测试（非全量测试），重新运行项目使用的 linter/类型检查。如果某个修复导致测试失败，回滚该修复并报告。
6. **汇总**你做了什么：按评审者类别和风险层级列出已应用的修复，以及你故意跳过的发现及其原因。

## 常见陷阱

- **别超过 ~3 并行。** 更多评审者意味着更多成本和更多冲突建议，而非更好覆盖。三个类别已覆盖全部。
- **给每个评审者完整的 diff。** 按文件拆分 diff 破坏了设计——跨文件重复和 N+1 只在全局视角下暴露。
- **评审者搜索，不猜测。** 一个没有指出现有工具函数在哪里的复用建议（"大概有辅助函数做这个"）是噪音。要求 `file:line` 证据；缺乏证据的发现直接丢弃。
- **应用 ≠ 重写。** 这是清理用户近期的改动，不是重构整个模块。编辑范围限定在 diff 触及的文件加上修复必需的最小改动。
- **遵守项目规范。** 如果仓库有 AGENTS.md / CLAUDE.md / linter 配置，把那些规则纳入评审者 prompt，让建议与项目风格一致。
- **大 diff 撑爆上下文。** 如果 diff 过大（>2000 行），在委托前缩小范围——三个 sub-agent 各携带 5000 行 diff 成本高且可能截断。
- **过度信任死代码工具。** `knip`、`ts-prune`、`depcheck` 会标记实际被动态使用（字符串导入、反射）的导出。在删除前始终 grep 搜索符号名——工具报告干净不等于真没人用。
- **重命名前检查公共接口。** 导出名、API 路径、数据库列名、配置键都是接口——即使名字不好，重命名会破坏消费者。把公共接口变更标记为 RISKY；绝不自动重命名。
- **删除"不必要"的错误处理。** 空 catch 块或被忽略的错误可能是有意的——该错误在那个上下文中是预期且无害的。标记它，别删它；让人来决定。
